# CLAUDE.md — RuneShare project rules

RuneShare: RuneScape 3 players sign in with Google and share plugin strings — **Watchdog alarm strings** and **tile marker presets**. Phoenix 1.8 + LiveView 1.2 + Ash 3 + Postgres.

Project rules for AI agents. Framework rules (Ash, Phoenix) live in Claude Code skills at `.claude/skills/ash-framework/` and `.claude/skills/phoenix-framework/`, generated by `mix usage_rules.sync`. No duplicate framework rules here.

## General guidance

### Ask if you don't know
Unsure how to do something, or what the user wants? Ask.

### Ash first
Use Ash concepts, almost never Ecto directly. Think hard "Ash way". Unknown? Look in the `ash-framework` skill + rules & docs of associated packages.

### Code generation
Start with generators where possible (`mix ash.gen.resource`, `mix ash.gen.domain`, …; pass `--yes`). Give a starting point, modify if needed.

### Logs & tests
When done changing code, compile, check logs or run applicable tests to see the effect.

### Seed data
`priv/repo/seeds.exs` = living "from-zero-to-running-system" script. Runs on `mix setup` / `mix ecto.reset`, must stay idempotent (look up first, create only if missing). Every new feature extends it so a fresh clone gives a full app with one command.

### Testing
Every feature ships with tests. One happy-path test plus obvious failure cases, through code interfaces. Two cases warrant more:

- **Authorization** — every update/destroy proves another user is forbidden; every create proves anonymous visitors are forbidden.
- **LiveViews** — PhoenixTest (`visit`/`click_button`/`assert_has`; Playwright driver for JS-dependent journeys) whenever the LiveView is interactive. Minimum: mounts, primary action works, auth redirects fire.

Never call Google from tests — drive `:register_with_google` with fake claims (`register_user!/1`). Details: `testing` skill.

## Parallel agents

Several agents may work this repo at once from sibling git worktrees. Each checkout owns a **slot** (`RUNESHARE_SLOT`, 0-9); every port and database name derives from it. Main checkout is slot 0 (port 4000, `runeshare_dev`).

**Run `mix runeshare.slot` before starting a server or assuming a URL.** Never hard-code 4000. Spin up a worktree with `bin/agent-worktree new <name>`.

Full workflow, port map and troubleshooting: `parallel-agents` skill.

## Project orientation

- App module `Runeshare`, source `lib/runeshare/`. Web layer `RuneshareWeb`, `lib/runeshare_web/`.
- Domains: `Runeshare.Accounts` (User, UserIdentity, Token — Google sign-in only; `update_profile` for the display name) and `Runeshare.Sharing` (Preset, PresetVersion, Like, Comment, Report, PresetCopy).
- **Versioning**: every `share`/`edit` writes an immutable `PresetVersion` snapshot (`number` 1, 2, 3…) via `Preset.Changes.SnapshotVersion`; `Preset.version` is the newest number and the Preset row always holds the newest content. Old versions live at `/presets/:id/v/:number`. An edit that changes no versioned field and has no change note (e.g. tags only) keeps the current version; an edit within `:version_merge_window_seconds` (30 min; 0 in tests) of the newest version's creation updates that version in place. The versions panel shows the newest 3 + the one on screen and folds the rest. Comments and likes belong to the preset, not a version.
- **Discovery**: `tags` (≤5, normalised by `Preset.Changes.NormalizeTags`, which also maps nicknames to standard tags via `Sharing.TagCatalog`; free tags allowed; the form picks tags with LiveSelect, suggestions from `TagCatalog.suggest/1`), `copy_count` (aggregate over `PresetCopy`, one row per preset + visitor; `record_copy!(preset_id, socket.assigns.visitor)` — `@visitor` comes from `LiveUserAuth`, `"user:<id>"` or `"anon:<session visitor_id>"`), `content_hash` (`find_duplicate_presets`), sorts `:newest | :most_liked | :most_copied`. `list_presets!(kind, %{search:, sort:, tag:}, opts)` — optional filters go in the params map, never positionally (positional optionals swallow keyword opts).
- **Moderation**: `User.role` is `:admin` for addresses in `ADMIN_EMAILS` (re-evaluated every sign-in). Admins bypass Preset/Report policies, can delete any comment, `hide_preset`/`unhide_preset` (hidden presets — and their versions, comments and likes — are visible only to author + admins; creates that hang off a preset use `Changes.RequireVisiblePreset`). `Report` (one per user+preset, `report_preset!(preset_id, reason, %{note:}, opts)`), `list_open_reports`, `resolve_report`.
- **Rate limits**: `Runeshare.Sharing.Validations.RateLimit` counts the actor's recent rows in the DB (10 presets/hour, 10 comments/5 min).
- **Real-time**: Ash `pub_sub` notifiers broadcast through `RuneshareWeb.Endpoint` on `presets:shared:<kind>`, `presets:deleted:<kind>`, `presets:<id>`, `likes:<preset_id>`, `comments:<preset_id>`. Each resource owns its topics: a `@topic` prefix shared by its `pub_sub` block and its `subscribe`/`unsubscribe` functions. LiveViews subscribe only through the domain (`Sharing.subscribe_to_kind/1`, `subscribe_to_preset/1`, `unsubscribe_from_preset/1`) — never `Endpoint.subscribe` with a hand-built topic. Notification data carries no loads — re-fetch through a code interface.
- **Logging**: `Runeshare.ActionLog` is the global `Ash.Tracer` — one line per action (actor id, duration, outcome, record id via `ActionLog.Notifier` in `simple_notifiers`). Don't add `Logger` calls around code-interface calls; log only what Ash can't see. Never log emails, tokens or action inputs. Prod is JSON (`config/runtime.exs`, metadata allow-list).
- **LiveView data loading**: use `stream_async`/`assign_async`/`start_async` with `<.async_result>` skeletons for lists; streams for anything that grows (comments, listings). Capture actor/ids in variables before the async fn — never reference `socket` inside it.
- **One `Preset` resource for both plugins**, discriminated by `kind` (`:watchdog_alarm | :tile_marker`, see `Preset.kinds/0`). A new plugin = a new kind, not a new resource. Per-kind labels and paths live in `RuneshareWeb.PresetComponents`.
- `content` is validated per kind by `Runeshare.Sharing.ImportString`: Tilemarkers = `TM2` + unpadded base64url (payload: version byte, name-length byte, UTF-8 name); Watchdog = JSON `{"schemaVersion", "pluginVersion", "entries": [{"name", "graph", …}]}`. It also reads names out of exports (form title prefill, "Alerts in this export" panel). A real sample of each lives in `test/runeshare/sharing/import_string_test.exs`; a new plugin kind needs a `check/2` clause there.
- **Cover images**: `Preset` `has_one_attached :cover_image` (AshStorage, pinned git dep — `StorageBlob`/`StorageAttachment` resources). `share`/`edit` take a `cover_image` file argument (`Preset.Validations.CoverImage` checks magic bytes, declared type, ≤ 2 MB); `edit` takes `remove_cover_image`. Load `cover_image_url`. Service: Disk in dev (served at `/storage` by `AshStorage.Plug.DiskServe`), `AshStorage.Service.Test` in tests (`cover_image/2` builder), public Tigris bucket in prod (`config/runtime.exs`). The form's `.ShrinkImage` hook re-encodes to WebP ≤ 1600 px before LiveView uploads.
- **Production**: Fly.io, see `DEPLOY.md`. Never run `fly` commands that create, scale or destroy resources without the user's go-ahead.
- Routes per kind: `/watchdog`, `/tile-markers` (+ `/new`); `/presets/:id` (+ `/edit`, `/v/:number`); `/account` (private profile + own shares). The LiveView `live_action` carries the kind.

## Project conventions

### Auth and actors
Google OAuth via AshAuthentication (`google` strategy, `UserIdentity` stores `iss`/`sub`). Credentials from `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` (`.env`); `Runeshare.Secrets` reads them. LiveViews get `@current_user` from `RuneshareWeb.LiveUserAuth` on_mount (`:live_user_optional`, `:live_user_required`, `:live_no_user`). Pass `actor: socket.assigns.current_user` to every code-interface call.

Policies live on the resource. Reads are public; creates need an actor; update/destroy need `relates_to_actor_via(:author)`. User emails are hidden from everyone but the user (field policy) — show `name` instead.

### Code interfaces are the only entry point
Layering: **resource** owns the logic for its data (actions, policies, pub/sub topics, subscribe functions) → **domain** composes resources into the API (code interfaces, plus plain functions like `Sharing.subscribe_to_preset/1` that combine several resources) → **web layer** calls only the domain. Non-action logic follows the same path: put it on the resource it belongs to, expose it from the domain. In practice:
- Permissions in templates come from the policies: `Sharing.can_edit_preset?(user, preset)` and the other generated `can_*?` functions, computed once into assigns (not per render). For per-row checks in lists, use a calculation on the resource (`Comment.removable_by_actor`). `can_*?` on read actions filters instead of refusing, so it can't gate a page; use `Accounts.admin?/1` for moderator-only pages and links.
- Multi-step workflows are one action (`Sharing.hide_reported_preset/2` resolves and hides in one transaction), not two calls from a LiveView.
- Helpers the web layer needs outside an action (import string checks, tag normalising and suggestions, version merge rules, limits, `preset_kinds/0`) are `defdelegate`s on `Sharing`. Web modules never alias `Runeshare.Sharing.<Resource>.*` internals.

- Define code interfaces on the domain (`define :share_preset, action: :share`).
- Call them from LiveViews and controllers — **never** `Ash.create!/2`, `Ash.Query`, or `load:`/`query:` options built ad hoc in web modules (credo `NoAdHocAshQueries` enforces). Need a load or filter? Add an action, argument, or `default_options`.
- **Never** call `Repo` outside explicit infrastructure code.

### HTTP
Use `Req` for outbound HTTP. Don't add `httpoison`, `tesla`, or `httpc`.

### Mix
- `mix format` and `mix credo --strict` before considering a change done.
- `mix precommit` when finishing a chunk of work: compile (warnings as errors), unused deps, format, skills drift check, credo, tests.
- Read `mix help <task>` before unfamiliar tasks.
- After adding ash_* or phoenix_* deps, re-run `mix usage_rules.sync --yes`.

### Migrations
After resource changes, run `mix ash.codegen --dev` iteratively, then a final `mix ash.codegen <feature_name>` at session end to consolidate.

## Code quality

`mix credo --strict` runs ~180 checks from four suites alongside standard Credo:
- **ExSlop** — AI slop: blanket rescues, narrator-style comments/docs, N+1 queries, redundant Enum chains, identity passthroughs.
- **ExDNA** — AST-aware clone detection. On a clone report, extract shared logic.
- **bylaw_credo** — Ecto/Ash query shape, HEEx accessibility (`type`, `alt`, `rel="noopener"`, labels, loading states), typespec discipline, LiveView return-tuple style.
- **llamex** — LLM-authored Ash/Phoenix code: ad-hoc Ash queries, authorization bypass, `self()` in LiveViews, redundant wrappers.

Every check is listed explicitly in `.credo.exs` under `checks.enabled` (an explicit list discards plugin-injected checks). `.credo.exs` also carries a commented backlog of parked checks with measured counts.

Suppress with `# credo:disable-for-next-definition <Check>` plus a reason comment — never by editing `.credo.exs` without sign-off. Details: `credo-checks` skill.

## Do not

- Don't use raw Ecto in domain code (use Ash).
- Don't use `String.to_atom/1` on user input.
- Don't set `require_atomic? false` without a justified reason.
- Don't write inline `<script>` tags in templates. Use colocated hooks (`:type={Phoenix.LiveView.ColocatedHook}`) or `assets/js/`. Exception: the root layout's `application/ld+json` block (data, not code), built by `RuneshareWeb.StructuredData` — pages assign `json_ld`.
- Don't reference external vendor scripts/CSS via `src`/`href`. Bundle through `app.js` / `app.css`.
- Don't use `@apply` in CSS. Don't add `tailwind.config.js`.
- Don't nest multiple modules in one file.
- Don't assign inside `if`/`case`/`cond` expecting mutation; rebind the result.

## Phoenix 1.8 specifics

- Begin every LiveView template with `<Layouts.app flash={@flash} current_user={@current_user}>`.
- Messages are LiveToast toasts, rendered by `LiveToast.toast_group` in `Layouts.app` only. In-page: `toast(socket, :info, msg)` (imported in LiveViews). Across a navigation: `put_flash/3` (shown as a toast). Both vanish after 5 s; no connection-lost notices.
- `<.icon name="hero-x-mark" class="size-5"/>` for icons; never `Heroicons` modules.
- `<.input>` from `core_components.ex` for form inputs.
